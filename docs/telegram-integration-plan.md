# OmniChat Telegram 接入开发计划

## 1. 项目目标

在现有 OmniChat Electron 客户端中正式开放 Telegram，提供与 WhatsApp 一致的账号管理、会话列表、聊天、媒体、翻译、头像、代理和后台同步能力。

Telegram 连接继续运行在用户本地客户端，不把账号登录态、手机号、API Hash 或 MTProto 会话上传到服务器。

## 2. 技术路线

### 主渠道：Telegram 普通账号

- 底层使用 [GramJS](https://github.com/gram-js/gramjs)
- npm 包：`telegram`
- 协议：MTProto
- 适用场景：个人号客服接待、联系人聊天、群组和频道会话
- 登录方式：扫码、手机号验证码、两步验证密码

当前实现位置：

- `client/src/main/channels/telegram-user/telegram-user-adapter.ts`
- `client/src/main/channels/telegram-user/mapper.ts`
- `client/src/main/channels/telegram-user/index.ts`

### 辅助渠道：Telegram Bot

- 使用 Telegram Bot API
- 保留现有 `telegram_bot` 适配器
- 适用场景：机器人客服、自动化通知和服务号
- 不替代普通账号，不与普通账号共用登录流程

### 暂不采用 TDLib

TDLib 能力更接近官方客户端，但需要维护 C++ 原生库、Windows/macOS 多架构构建、Electron 原生模块打包和签名。当前项目已有 GramJS 基础，迁移 TDLib 的成本和风险明显更高。

## 3. 当前已有基础

- Telegram 普通账号插件已经注册到渠道注册表
- GramJS 依赖已安装
- 普通账号支持扫码和手机号登录
- 登录会话可以持久化，重启后免重复验证
- 已支持文本、图片、语音、视频和文件收发
- 已支持 SOCKS 代理和账号级设备指纹
- 已支持账号头像、会话标题和联系人 ID 获取
- 已接入统一会话列表、翻译管道、本地消息存储和后台同步
- Telegram mapper、API 凭证解析和代理逻辑已有单元测试

当前未完成的主要是产品开放、功能补齐和真实账号验收。主页及部分中文文案仍显示“即将支持”，需要在验收通过后统一切换。

## 4. 开发阶段

### 阶段一：账号接入正式开放

- 将主页 Telegram 状态从“即将支持”切换为“可用”
- 账号新增入口显示“Telegram 账号”和“Telegram Bot”两种类型
- 普通账号默认优先显示扫码登录，同时保留手机号登录切换
- 完善登录中、验证码错误、两步验证、会话过期和网络错误提示
- 登录成功后显示 Telegram 昵称、用户名、手机号和在线状态
- 补充中英文等多语言文案

验收：新增 Telegram 普通账号，扫码和手机号两种方式都能完成登录；重启客户端后可自动恢复会话。

### 阶段二：会话与联系人能力

- 拉取私聊、群组、超级群和频道会话
- 显示联系人头像、昵称、用户名和手机号（平台返回时）
- 支持会话搜索、未读数、置顶、静音、删除和清空聊天记录
- 完善群组列表和群组创建入口
- 区分普通联系人、群组、频道和机器人会话
- 处理 Telegram 私聊 ID、群组 ID、频道 ID 的稳定映射

验收：同一账号在手机端产生的新消息能实时出现在客户端；群组和私聊不会串号，重启后会话仍可打开。

### 阶段三：消息和媒体完整性

- 文本消息实时接收和发送
- 图片、视频、语音、文件的下载、预览和发送
- 语音条统一转为 Telegram 兼容格式
- 处理回复、转发、编辑、撤回和媒体下载失败状态
- 明确大文件限制和失败提示
- 出站翻译沿用现有翻译管道，确保发送前翻译和聊天记录展示一致

验收：覆盖文本、图片、视频、语音、文件五类消息；发送失败时消息状态明确为失败且可重试。

### 阶段四：头像、在线状态和资料实时更新

- 连接成功后拉取账号自身头像
- 打开会话时按需刷新客户头像
- 头像变化后更新本地缓存，不依赖客户端手动上传
- 根据 Telegram 更新事件刷新昵称、用户名、头像和在线状态
- 区分在线、离线、异常和未连接状态
- 网络断开后自动重连，避免错误覆盖已有头像和资料

验收：手机端修改头像后，客户端刷新或重新打开会话能显示新头像；网络断开时状态变为异常/离线，恢复后自动回到在线。

### 阶段五：代理、多账号和安全

- 每个 Telegram 账号独立代理配置
- 普通账号 MTProto 只使用 SOCKS4/SOCKS5 或 Telegram 支持的连接方式
- HTTP 代理需要明确提示不适用于普通账号 MTProto
- 每个账号使用稳定但不同的设备指纹
- API ID/API Hash 只保存在本地配置或安全的构建注入中
- StringSession 只保存在本机，不进入云同步、不上传后台
- 删除账号时清理本地会话、缓存头像和事件监听
- 禁用账号后停止接收消息，重新启用后再连接

验收：同时运行多个 Telegram 账号时，代理、会话、头像和消息不交叉；检查同步 payload 不包含 API Hash、StringSession 和代理密码。

### 阶段六：后台同步与工单适配

- Telegram 会话和消息写入现有本地 MessageStore
- 通过现有 SyncClient 同步聊天记录、译文、头像和联系人标识
- 工单账号列表增加 Telegram 平台筛选
- 账号统计区分 WhatsApp、Telegram、Telegram Bot
- 头像、手机号、昵称字段沿用统一账号资料结构
- 重粉、客户继承和工单统计使用统一 contactId 规则
- 对 Telegram 没有手机号的用户，使用稳定的 Telegram 用户 ID 作为平台内联系人标识，并标记来源平台

验收：Telegram 会话可在管理后台查看；工单统计不因 Telegram 用户没有手机号而丢失或错误合并客户。

### 阶段七：正式发布和回滚

- 增加 Telegram 功能开关，默认仅对内部测试账号开放
- 完成 macOS Apple 芯片、macOS Intel、Windows x64 三个平台打包
- 测试扫码登录、手机号登录、代理登录、重启恢复和升级覆盖安装
- 记录 GramJS 错误、登录失败原因、重连次数和媒体失败原因
- 灰度开放后观察 3-7 天，再对所有用户开放
- 保留关闭 Telegram 插件的远程配置或本地开关，出现协议兼容问题时可快速停用

## 5. 统一数据约定

### 账号

```text
kind: telegram
accountId: 本地生成的账号 ID
credentials.session: GramJS StringSession，仅本地保存
credentials.phone: 登录手机号，可选
credentials.apiId/apiHash: 高级覆盖项，不进入云同步
proxyUrl: 账号独立代理
```

### 会话

```text
conversationId: telegram:<accountId>:<externalChatId>
```

群组和频道必须保持稳定的 externalChatId，不能使用显示名称作为主键。

### 联系人

- 有手机号时优先使用规范化手机号
- 无手机号时使用 `telegram:<userId>`
- 群组、频道和机器人不参与普通自然人客户合并

## 6. 测试计划

### 单元测试

- Telegram 用户、群组、频道 ID 映射
- 私聊、群组、频道消息映射
- 文本和媒体消息映射
- 登录状态机：扫码、手机号、验证码、两步密码、失败和停止
- StringSession 保存与清理
- 代理配置解析
- 头像为空、头像更新和网络失败保留旧头像
- 联系人 ID 稳定性

### Electron 端到端测试

- 新增 Telegram 普通账号入口
- 扫码登录界面
- 手机号登录流程
- 发送和接收文本
- 媒体消息
- 账号退出、删除、禁用和重新启用
- 代理配置后连接
- 客户端重启恢复登录
- Telegram 与 WhatsApp 会话混合显示但不串数据

### 生产验收

- 至少 2 个真实 Telegram 普通账号
- 至少 1 个开启两步验证的账号
- 至少 1 个 SOCKS5 代理
- 私聊、群组、频道各一组消息
- 头像修改前后对比
- 手机端发消息、客户端回复、后台同步三端闭环

## 7. 主要风险与处理

| 风险 | 处理方式 |
|---|---|
| Telegram 登录风控或验证码限制 | 降低登录重试频率，持久化 StringSession，避免频繁注销重登 |
| 账号批量操作导致限制 | 默认只做被动接收和人工回复，不实现群发、批量加人等高风险功能 |
| GramJS API 变更 | 将 SDK 访问集中在 adapter，mapper 保持纯函数并锁定测试 |
| macOS/Windows 原生打包差异 | 继续使用纯 Node GramJS，避免引入 TDLib 原生二进制 |
| 代理协议不兼容 | 普通账号明确区分 SOCKS 与 HTTP，连接前校验并显示错误 |
| API Hash 或会话泄露 | 禁止进入云同步、日志和后台接口，敏感字段全部脱敏 |
| Telegram 用户没有手机号 | 使用 `telegram:<userId>` 作为联系人标识，禁止与未知手机号强行合并 |

## 8. 建议执行顺序

1. 先完成阶段一和阶段二，放开 Telegram 登录、会话列表和联系人资料。
2. 再完成阶段三和阶段四，确保消息、媒体、头像和状态达到可用标准。
3. 接入阶段五和阶段六，验证代理、多账号、后台同步和工单统计。
4. 最后做阶段七灰度发布，不建议在真实用户全部开放前迁移到 TDLib。

## 9. 完成标准

当以下条件全部满足时，Telegram 才从“即将支持”改为正式“可用”：

- 普通账号扫码和手机号登录均可用
- 重启后可恢复登录，不要求用户重复验证
- 私聊、群组至少支持文本和常用媒体收发
- 头像、昵称、联系人 ID 和在线状态正确
- 多账号和代理互不串号
- 客户端禁用、退出、删除行为正确
- 管理后台和工单能看到 Telegram 数据
- 敏感凭证未进入云同步、日志和后台
- Windows x64、macOS Apple 芯片、macOS Intel 安装包均通过冒烟测试
